# Skill composition: skill map

Per-flow map of which pack item should own each conductor step, what supports it, where ponytail applies, and where the
owner sees the model's decisions. Made 2026-10-22/23 for [flow.md](flow.md) Phase 2.

How it was made, and how far to trust each part:

- **Catalog** (481 entries; workflow `wf_4c4976e2-f43`, six read-only readers): superpowers 7.0.1 (vendored), ponytail
  (vendored), mattpocock-picks and pstack-picks with their upstream catalogs at the pinned shas, tob-picks with Trail of
  Bits' catalog, self-review, the official plugins installed here, the tools and domain packs, and Claude Code 2.1.307's
  built-ins (docs plus the binary's strings). The raw JSON is in the session scratchpad, not the repo.
- **Maps of feature-flow, research-flow, verify, test-audit, understand and learn**: one mapper agent per pair, from
  the catalog. The skeptic pass that should have checked them was cut off by the usage limit, so **they are
  unverified**: treat every path:line in them as a lead.
- **Maps of implement, fix-flow, upgrade, doc-audit, harden, integrate and vendor-a-pack**: written by me in the main
  session (the owner asked to stop the workflow to save usage), from each SKILL.md and the catalog's candidates. Also
  unverified by a second reader.
- No synthesis or completeness-critic agent ran. The cross-cutting part below is mine.

## Facts the catalog settled

- `${CLAUDE_PLUGIN_DATA}` for flows is `~/.claude/plugins/data/flows-dead-claude-skills/`
  ([plugins/components](https://code.claude.com/docs/en/plugins/components#reference-plugin-paths-and-store-data);
  `ls ~/.claude/plugins/data` matches the naming). It is substituted in flows' own SKILL.md text, not inside a pack's
  SKILL.md that a conductor reads by path; no vendored superpowers or ponytail skill uses a variable, so nothing is lost.
- The Skill tool refuses a dmi skill with "Do not replicate this skill's workflow by other means" unless the user typed
  its `/name` this turn. A file read by path never goes through the Skill tool, so conductors reading packs by path don't
  meet that refusal; the risk is only a conductor (or Claude) calling the Skill tool on a pack skill first.
- Bundled `commit` and `pr` skills exist in the binary but are off on this machine (a rollout gate); `/autofix-pr`
  pushes with no gate. Only the user can start `/verify` (bundled), `/batch`, `/doctor`, `/deep-research`.
- Only the main session can ask the owner (AskUserQuestion) or start a workflow; subagents can't. Every stop that must
  reach the owner during a build has to pass through the coordinating session.
- Three pstack upstream skills that aren't vendored bear directly on the .NET case: `principle-laziness-protocol`
  ("a new signal through types, schemas or pipelines: stop, find a more direct path", SKILL.md:15 at 4e5b1cf),
  `principle-migrate-callers-then-delete-legacy-apis`, and `principle-never-block-on-the-human`, which states the
  opposite of the owner's gates (proceed, then present) and is the stance SDD's "Rulings, not stalls" takes.

## Cross-cutting findings

1. **The build has no stop for decisions the plan didn't make** (every build flow: feature-flow 6b, research-flow 6,
   implement 3, fix-flow 4, upgrade 3, harden 4). superpowers SDD rules and continues
   (`plugins/shared/superpowers/skills/subagent-driven-development/SKILL.md:17-31`); the implementer's own escalation
   (`implementer-prompt.md:80-84`) reaches only the controller. Settlement, as agreed with the owner: a fifth stop in
   the conductor's own text (so it is re-attached after compaction), a deviation clause added to every implementer and
   task-review brief, and a per-task check of changed files against the task's Files list. The mappers add two needs no
   pack meets: a **Rulings** section in flow.md where the build's own small calls land as they are made (SDD and
   executing-plans delete their ledger at finish, so /learn and the owner never see them), and a **Decisions** row in
   /verify's verdict that the owner confirms or reopens before the branch is approved.
2. **Where cross-cutting concerns are resolved is never asked.** feature-flow's map puts `codebase-design`,
   `principle-boundary-discipline` and `principle-redesign-from-first-principles` into Brainstorm (the approaches
   message names, for each cross-cutting concern, the seam where it is resolved and which modules never see it), Grill
   (one design-tree branch per concern) and Plan (each seam copied verbatim into writing-plans' Global Constraints, so
   implementers and reviewers get it). implement has no design phase, so its Read phase needs the same question when
   the input doesn't answer it.
3. **Packs not installed: what needs special handling.** Skills read by path work as plain text. What doesn't come for
   free: agents (self-review's, tob's `spec-compliance-checker` and `sharp-edges-analyzer`, pstack's `comment-sicko`)
   exist as `subagent_type` only when their plugin is installed, so a conductor must pass the agent file's text as a
   `general-purpose` prompt; tob's `spec-compliance` workflow runs only from an installed plugin or a script path;
   Skill-tool cross-references inside a pack ("invoke superpowers:writing-plans") must be overridden by the conductor
   (flow-rules already does this for handoffs); the brainstorming visual companion needs its server script at a real
   path; ponytail's hooks (mode tracker, codebase map, levels, band) are gone, and the conductor passes the rule text it
   wants at each step instead.
4. **ponytail at chosen steps.** The maps converge on: `before-you-write` (reach list) in Plan and in each implementer
   brief; `smallest-complete-change`, `bug-fix-rule` and `never-cut` in implementer briefs and fixes; the `lite`
   smallest-option row as one option at Brainstorm and at report gates; `ponytail-review` as the Simpler angle of the
   plan review and in harden; `ponytail-debt` over the branch's added lines at Finish; nothing in Ground, Reproduce,
   Research, Understand or Learn. The reply footer goes into reports ("Not checked"), not every message. Conflicts to
   settle in the conductor: ponytail's "no test for trivial changes" vs TDD (TDD wins inside build flows; the test rule
   only decides test-audit's recommendations), ponytail's smallest-version vs brainstorming's full design (the smallest
   version is one option, the owner picks).
5. **Duplicates to resolve** (from grounding, unchanged): code-review@official vs self-review's bug pass; the suite run
   three times in /verify; pr-test-analyzer in /self-review and /test-audit (the verify map passes self-review's report
   into test-audit instead); writing-skills vs skill-creator; three homes for specs and plans.
6. **Language and domain packs**: no conductor names one. The maps place csharp-skills (`dotnet-webapi`, `data`,
   `optimizing-ef-core-queries`, `run-tests`, `binlog-failure-analysis`, `migrate-dotnet`, `test-gap-analysis`),
   rust-skills, postgres (`schema-design`, `postgres-database-migration`) and hallmark at Plan, Execute, Cause, Bump and
   test-audit's Fill, chosen by the project's manifest files. That needs one rule in flow-rules: detect the stack
   (`*.csproj`, `Cargo.toml`, migrations, a web frontend) and add the matching pack to the briefs.
